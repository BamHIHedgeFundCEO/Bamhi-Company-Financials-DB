### 公司檔案：`submissions.json` 免費附送，零額外請求

有值：`name` / `tickers` / `exchanges` / `sic` / `sicDescription` / `entityType` /
`category`(申報人規模) / `stateOfIncorporation` / `fiscalYearEnd` / `ein` / `phone` /
`addresses` / `formerNames`（含改名歷史與生效日）

**永遠是空字串，別指望：`website`、`description`。**
→ 業務散文只能來自 Item 1 Business 的 HTML（屬 D 階段）。

### Form 4 是純 XML，品質最好的一塊，且一份資料兩用

`https://www.sec.gov/Archives/edgar/data/{cik}/{accession_nodash}/form4.xml`
（`primaryDocument` 欄位會寫成 `xslF345X06/form4.xml`，**去掉 `xslF345X06/` 前綴**才是原始 XML；
帶前綴的是 SEC 的 XSL 轉譯 HTML 版）

實測 AAPL `0001140361-26-032884` 的欄位：

```
rptOwnerName    = Newstead Jennifer
isOfficer       = true
officerTitle    = SVP, GC and Secretary
transactionCode = S      transactionAcquiredDisposedCode = D
transactionShares = 1439   transactionPricePerShare = 307.75
sharesOwnedFollowingTransaction = 40107
aff10b5One      = true     ← 10b5-1 預設交易計畫，「結構化欄位」不是註腳
```

AAPL 光是 `filings.recent` 裡就有 587 筆 Form 4。

**判讀規則（必須內建，否則做出來會誤導）：**
多數 Form 4 是 `A`（股權獎勵）與 `M`→`S`（行權後依 10b5-1 自動賣出）——**那不是看空信號**。
真訊號是 `P`（公開市場買入）與 `aff10b5One=false` 的 `S`。
UI 必須把兩類分開，不可混算成「本季內部人賣出 $X」。

**副產品：高管名單不必另做。** `officerTitle` 就是高管名冊，還自帶持股與變動。
（原本想抓的「歷史創始人」不在 SEC，已改成高管名單。）

### companyfacts 不含任何自訂命名空間

實測 AAPL `['dei','us-gaap']`、TSLA/BRK.A `['dei','ffd','us-gaap']`、NVDA、JPM 同。
→ 「用 companyfacts 建自訂標籤對照表」不是難，是**不可能**。
自訂標籤只能從 XBRL instance 或 DERA Financial Statement Data Sets 取得。

### 全公司標籤盤點只能靠 DERA Financial Statement Data Sets

`https://www.sec.gov/files/dera/data/financial-statement-data-sets/2025q3.zip` = 127,842,298 B
內含 `sub.txt`(6,541 申報 / 5,909 CIK)、`num.txt`(542MB)、`pre.txt`、`tag.txt`(83,782 標籤：標準 8,277 / 自訂 75,505)

**陷阱：`tag.txt` 的 `version` 欄位對自訂標籤而言，是「定義該標籤的申報書號」，
前綴是申報代理商的號碼、不是公司 CIK。**用前綴比對算每家公司的自訂標籤會全錯
（實測 NVDA 會算成 1、TSLA 會算成 0）。
正確做法是三表 join：`num.adsh` → `sub.cik`，再用 `tag.custom='1'` 過濾。
正確結果：JPM 20 / TSLA 18 / AAPL 3 / NVDA 1，**且沒有一個是營收標籤**
（SEC DQC 規則會逼申報人在主要報表上用標準標籤）。

## LLM 決策：不用 LLM，也不需要

原本以為 C/D 階段（CAMs / MD&A / 業務概況 / 指引展望）非 LLM 不可。不是。

**這四項的原文本來就是人寫的散文，直接原文直出 + 錨點 + EDGAR 連結即可。**
LLM 唯一真正的用途是「翻成中文並濃縮」，那是加值層不是必要層，而且它正好是
唯一會違反「資料一定是正確」的一層。

**定案：**

- 主線一律 **零 LLM、零 API 成本**：抽出原文段落，附 `Item 1A` 之類的來源標籤與 EDGAR 連結
  （參考站那個小標籤做法是對的，抄它）
- 若日後真的要中文摘要 → **離線批次跑在自己機器上**（本機模型或手動），產物存成 JSON
  提交進 repo / Blob，執行期零成本、零延遲、可人工覆核
- **數字層永遠不經過 LLM。** 這條不可協商

### 階段 0 — FSDS 覆蓋率盤點工具

**為什麼排第一：** 它的產出直接決定階段 A 摘要頁能放哪些欄位。
「不會有 n/a」不能用猜的，要有全市場密度數據支撐。

**做什麼：** `tools/fsds_coverage.py`
吃一包 FSDS 季度 zip，離線盤點 `config/xbrl_zh_map.json` 在全部 5,909 家上的覆蓋率。
**per-company 零 SEC 請求。**

**要回答的問題：**
1. 每個科目的全市場命中率（有多少家真的抓得到）
2. 依 SIC 產業分組的命中率 → 哪個科目在哪個產業整片抓不到
3. 抓不到的那些公司實際用了什麼標籤（候選補進 alias 清單）
4. 哪些科目密度夠高，可以進摘要頁而保證不出現 n/a

**必須避開的坑：**
- `version` 前綴比對 → 錯，要三表 join（見上）
- 只看 `num.txt` 有沒有該 tag 是不夠的：管線還有維度過濾與期間長度過濾，
  掃描要模擬管線的 fallback 層級，否則假陰性滿天飛（`coverage-sweep-false-negatives`）
- `num.txt` 542MB → 串流讀，不要整包進記憶體

**驗收：** 產出一份分產業的缺口報告；抽三個報告說「抓不到」的公司，
用 `tools/coverage.py` 打真 SEC 驗證確實抓不到。

#### 已完成（2026-08-20，commit `ea74e97`）

`python tools/fsds_coverage.py 2025q3.zip`（可餵多包合併）

**產出的第一個修法：**現金淨變動補上 `…PeriodIncreaseDecreaseExcludingExchangeRateEffect`
→ 全市場命中率 **76.5% → 98.7%**，map v1.5 → v1.6。

**驗證缺口的正確問法（踩過才知道）：**
- 問「這家歷史上用過我們收的標籤嗎」→ 假警報率 **87%**
- 問「這家在**那幾期**用了嗎」→ 假警報率 **3%**

網站呈現的是特定期間，所以缺口的單位是「**期**」不是「家」。
比對時要用 FSDS 的 `ddate` 對 companyfacts 的 `end`。

**通用摘要頁（所有產業都 ≥90%）目前 6 個：**
營業活動現金流量、本期淨利、資產總計、負債總計、現金淨變動、籌資活動現金流量

**分產業可上摘要頁的欄位數：**其他製造業 20 / 生技製藥 19 / 其他服務業 17 /
銀行與信貸 15 / 控股與投資機構 8

→ **摘要頁必須分產業樣板**，這點已由數據證實，不是猜的。

**低分 ≠ map 壞掉。**生技製藥「非利息收入」0%、軟體業「存貨」低，都是正確的
——那種格子該顯示「—」（不適用）不是 n/a。工具的第二部分才是要動手修的清單。

**尚未處理的候選（第二部分還有）：** `AccountsPayableAndAccruedLiabilitiesCurrentAndNoncurrent`
(309 家)、`DeferredRevenue` / `DeferredRevenueNoncurrent`(96 家)。
`CommonStockSharesIssued` 雖然分數最高**但絕對不能加**——SharesIssued 含庫藏股，
會讓市值高估。

#### 逐家適用性（取代產業層當第一順位）

產業表判不出同業裡的異類，所以再做一層**逐家**：問這家公司自己的報表
（FSDS `pre.txt` 的 IS/BS/CF）上有沒有語意相當的那一行。有 → 真缺口，維持 `n/a`；
沒有 → 不適用，寫「—」。產物 `config/company_applicability.json`（211 KB，7,093 家）。

執行期兩層，**逐家優先、不跟產業表取聯集**（衝突時逐家才對，取聯集等於讓差的那份也有票）；
逐家沒收錄才退回產業表，兩層都沒有就維持 `n/a`。

資料範圍：**四季 FSDS 聯集**（2025q3/q4、2026q1/q2）。一季只有 10-Q（20-F 僅 94 家），
2026q1 那季有 4,262 份 10-K + 372 份 20-F，補上外國發行人與非曆年公司。
一季 5,542 家 → 四季 7,202 家。

三個和產業層不同的關鍵設定，每個都是踩過才知道：

1. **自訂命名空間也算證據。** 覆蓋率報告只看 us-gaap/ifrs/srt，但適用性問的是
   「這一行存不存在」。公司用自訂標籤報存貨，那一行就存在，而且 companyfacts
   抓不到它 —— 那是**真缺口**，要留 n/a。判成不適用會把洞藏起來。
2. **多季 union。** 10-Q 比 10-K 短，只看一季會把年報才有的行判成不適用。
3. **看不清楚就不判。** 三張表任一張看到的標籤數 < 8 就整家跳過（107 家），
   退回產業表。沒申報過的公司完全不會出現，不會被判成「什麼都不適用」。

**執行期護欄（`financials.ts`）：只要該科目在任何一期抓到過值，就一定適用。**
適用性表是一家公司一個旗標、不分期間，而它判的是「有沒有出現在報表正面」。
蘋果與波克夏的使用權資產只在租賃附註、不在資產負債表正面 → 被判不適用，
但 companyfacts 抓得到、20 期有數字。沒這道護欄同一列會同時出現數字和「—」。

| | 原始 | 產業層 | 逐家層 | 「—」 |
|---|---|---|---|---|
| AAPL | 6.4% | 4.7% | **4.7%** | 95 |
| REGN | 8.9% | 7.0% | **8.0%** | 22 |
| JPM | 19.0% | 8.0% | **9.1%** | 339 |
| BRK.A | 23.8% | 18.1% | **18.9%** | 132 |

**n/a 率比產業層略升是預期的** —— 逐家層把產業層猜錯的「—」退回 n/a（BRK.A 的
營業成本／毛利、JPM 的應付帳款／應收帳款，那些公司報表上真的有那一行）。
四家有值格數逐字不變，且沒有任何一列同時出現數字與「—」。

**BRK.A 已修好的部分：**流動資產合計／流動負債合計／短期借款／營業利益四項
由 `n/a` 改為「—」（未分類資產負債表 + 無營業利益小計），這是產業層做不到的。

##### 誤判稽核（`--audit-na`）

誤判成「不適用」是唯一會說謊的方向，所以做了一支專門攤開它的稽核：列出所有
「判成不適用、但該公司報表上有分數 1.5–3.0 的標籤」的組合。第一次跑抓到真問題：

> **`Cash`（491 家）與 `CashAndDueFromBanks`（52 家）不在 map 裡。**
> 877 家的資產負債表只用這兩個標籤（US Bancorp、M&T、AIG、Loews、American Airlines
> 都在內）。隨機抽 14 家做**期間比對**，6 家有只靠這兩個標籤才拿得到的期
> （Cathay General 30 期）→ 會被寫成假的「—」。已補進 map v1.7，補完後
> 「現金」整條從稽核清單消失。

稽核清單剩下的都確認是不同的東西（par value ≠ 庫藏股、銀行薪資 ≠ SG&A、
折舊 ≠ 營業成本、應付稅款 ≠ 短期借款），維持不適用。

用 `num.txt` 的同業實際申報率（跟 `pre.txt` 詞元完全不同的訊號）檢查 36,657 個

| 同業申報率 | 組合數 | 佔比 |
|---|---|---|
| < 15%（強烈支持） | 13,953 | 38.1% |
| 15–50% | 14,902 | 40.7% |
| 50–85% | 6,229 | 17.0% |
| **≥ 85%（可疑）** | **1,573** | **4.3%** |

可疑的 4.3% 抽 16 個查 companyfacts：10 個被執行期護欄擋下，6 個真的會寫「—」，
而那 6 個逐一查證**全部是對的**：

##### 兩個試過但更糟的收緊法（不要再試）

`NA_MIN_SCORE = 3.0` 是**刻意調寬**的，寬到有已知偽陽性。收緊過兩次都更糟：

| 做法 | 動機 | 結果 |
|---|---|---|
| 核心詞（60% 標籤共有且 idf ≥ 2.0） | `income`+`expense` = 3.44 就過門檻，`NonoperatingIncomeExpense` 被當成蘋果有申報淨利息收入 | 長期負債判不適用 85 → **2,743 家**（`NotesPayableNoncurrent` 沒有 long/term）、合約負債 871 → 4,501 |
| 贏面（不到最高分的 1/1.25 就不算） | `IncomeLossFromContinuingOperationsBefore...NoncontrollingInterest` 含 interest | 營業收入判不適用 59 → **923 家** |

兩者都是拿偽陰性換偽陽性，方向反了。偽陽性只讓格子留在 n/a（難看但誠實）；
偽陰性把真缺口寫成「—」（說謊）。

##### 第三層：結構性否決（structural，唯一可以蓋過逐家的東西）

上面說的「蘋果淨利息收入顯示 n/a」不是個案，是**系統性**的：逐家判斷靠標籤詞元
比對，而「淨利息收入」的詞元全是泛用字（interest／income／expense），幾乎每張
損益表都有含 `income`+`expense` 的標籤。實測 7,093 家裡只有 **110 家**被判不適用
—— 整片非金融業的淨利息收入都在顯示 n/a，佔 18 家抽樣殘餘 n/a 的 16%。

先試過從詞元下手，兩條都不划算（實測數字）：

| 做法 | 淨利息收入判不適用 | 副作用 |
|---|---|---|
| 去除 `NoncontrollingInterest` 再斷詞 | 110 → 124 | 幾乎沒用 |
| 再加「重疊詞不能只有 income/expense」 | 110 → 1,136 | 所得稅費用 316 → **1,191**、利息費用 76 → **599** |

改用產業統計否決。`concept_applicability.json` 因此有兩份清單：

- `not_applicable`（同業申報率 <15%）—— **只在逐家表沒收錄該公司時當退路**
- `structural`（<8%）—— **一律與逐家判斷取聯集**

門檻 8% 不是隨便挑的，是逐一查證翻面結果選出來的：

| 門檻 | 18 家抽樣 n/a 率 | 翻面內容 |
|---|---|---|
| 現況（無否決） | 11.3% | |
| <8% | 8.7% | 23 個翻面**全對**（非金融業的淨利息收入、券商的營業成本／毛利、銀行與 REIT 的研發費用） |
| <15% | 7.2% | 開始說謊：JPM／美銀的**應收帳款**、波克夏的**營業成本與毛利** —— 那些公司報表上真的有那一行 |

##### 兩道閘門，缺一個就滿是噪音

單靠標籤詞元比對會產出這種候選：`DeferredIncomeTaxLiabilitiesNet`（遞延所得稅）
被指給「合約負債」1,033 家、`ProceedsFromSaleOfPropertyPlantAndEquipment`（處分收入、
方向相反）被指給「資本支出」95 家。兩個都是被 `deferred`／`property plant equipment`
這種共同詞帶過門檻。

加上**行標題閘門**（pre.txt 的 `plabel`＝申報人自己印在報表上的那行字）之後，
資本支出候選 848→488、應收帳款 619→269、所得稅 138→43。標籤名被分類法的命名慣例
帶偏，行標題被公司自己的簡寫帶偏，兩者錯的地方不一樣，取交集才留得下真的。

##### 驗證方法：期間比對，不是看名字像不像

對每個候選打 live companyfacts，在**兩邊都有值的期**上比數值。真同義詞會相等或呈
穩定倍數，不同一條的會亂。五個故意放進去的對照組全部被擋下：

| 對照組（已知錯） | 重疊期相等 | 中位倍數 |
|---|---|---|
| `LiabilitiesAndStockholdersEquity` → 股東權益 | 0 / 34 | 6.18 |
| `ProceedsFromSaleOfPropertyPlantAndEquipment` → 資本支出 | 0 / 140 | 0.03 |
| `AccretionAmortizationOfDiscountsAndPremiumsInvestments` → 折舊攤銷 | 0 / 120 | **−0.57** |
| `AccruedLiabilitiesCurrent` → 應付帳款 | 0 / 155 | 6.00 |
| `DeferredIncomeTaxLiabilitiesNet` → 合約負債 | 0 / 60 | 2.69 |

也擋下兩個看起來很合理的：`PaymentsToDevelopRealEstateAssets`（0.14）與
`PaymentsToAcquireOtherProductiveAssets`（0.31）只是資本支出的**子項**，收進來會把
REIT 的資本支出少報八成 —— 錯的數字比 n/a 更糟。

##### ⚠ 最大的陷阱：map 的 tags 會餵進適用性的 idf

**在 A 科目加一個 alias，會靜靜地改掉 B 科目對幾百家公司的判定，方向還是說謊的那一邊。**
這件事在覆蓋率、命中率、n/a 總數上全都看不出來（總數還會變好看，因為「—」不算 n/a）。

實測兩次，都是為了修個位數家數而弄壞上千格：

|---|---|---|---|
| `LimitedLiabilityCompanyLlcMembersEquity…` | 5 家 | **1,622 格** | `LimitedLiability` 貢獻 `liability` 一詞 → 其 idf 3.22→2.81 → 靠 {liability, lease}／{liability, deferred} 得分的標籤整批跌破 3.0 → 長期租賃負債 808 家、合約負債 814 家從 n/a 翻成「—」，抽 10 家有 4–5 家其實有申報 |

#### 行標題撤銷（`build_evidence` 的第二道閘門）

適用性的證據原本只看標籤詞元，所以 `OperatingLeaseLiabilityNoncurrent` 會因為
{liability, lease} 被當成「這家公司有長期負債那一行」的證據 —— 真的沒有的公司也
維持 n/a。修法**不是**把詞元門檻調嚴（試過兩次都反效果），而是引進獨立訊號：
申報人自己印在報表上的那行字。規則只往單一方向作用：

| 行標題 | 動作 |
|---|---|
| 明確指名**別的**科目 | 撤銷這條證據 |
| 對這個科目也夠分 | 留著（兩個訊號一致） |
| 對每個科目都不夠分（"Other"、"Total"、公司簡寫） | **留著** —— 含糊不代表沒有 |

第三條是安全閥，少了它 terse label 的公司會整片被誤判。直接對照（標籤就在 map 的
`tags` 裡）不受閘門影響 —— 公司把 Inventory 那行叫什麼都不改變它是存貨。

### 負債總計把非控制權益算進去了（map v1.9）

量「僅維度／自訂標籤」兩桶的可行性時撞到的既有缺陷，跟 n/a 無關 —— 它是**已經在
顯示的錯數字**，而且畫面上完全看不出來，就是個看起來正常的數字。

`Liabilities` 這個標籤很多大公司根本不報（資產負債表上沒有「負債總計」那一行）：
WMT、INTC、DIS、KO、ORCL、CHTR、SRE、HON、ACN 都是，全靠 `derive` 推算。原式是
`total_assets - equity`，而 `equity` 的標籤優先序是 `StockholdersEquity`（**母公司
單獨**）在前 —— 這是對的，ROE 的分母要配母公司淨利 —— 於是非控制權益與可贖回權益
就一起被算進了負債。

#### 實測（2026q1+q2，只取 USD，容差 max(負債 0.5%, 資產 0.2%, $1,000)）

在 **`Liabilities` 有申報**的 15,237 個期上比對，因為只有那裡才驗得出對錯：

| 規則 | 對 | 錯 | 寫錯率 |
|---|---|---|---|
| 現行　`資產 − equity` | 11,612 | 3,625 | **23.79%** |
| 只換權益優先序　`資產 − equity_total` | 13,432 | 1,805 | 11.85% |
| **`資產 − equity_total − temporary_equity?`** | **14,516** | **721** | **4.73%** |

也試過「規則二：沒有含 NCI 的憑據就放棄（寫 n/a）」—— 寫錯率 4.8% 一樣，但放棄了
10,308 個期，其中絕大多數本來就算得對。放棄不是免費的，這裡沒有理由付。

#### 落地

新增兩個 **`internal: true`** 科目（參與推算、不輸出成報表列）：

- `equity_total` 標籤優先序刻意與 `equity` **相反**：先取
  `StockholdersEquityIncludingPortionAttributableToNoncontrollingInterest`
- `temporary_equity` 可贖回特別股／可贖回非控制權益。GAAP 擺在負債與權益之間、
  兩邊都不算。絕大多數公司沒有這一塊，所以在推算式裡寫成選用項 `?`（缺值當 0）。
  `?` 只作用在推算式內部，**不會產生任何顯示的 0**

`derive` 因此從二元擴充成多項左結合（`a - b - c?`）。設定層表達不出「缺值當 0 的
選用項」，這是少數該改程式碼的情形。

⚠️ 內部科目的 tags **不進 `tools/fsds_coverage.py` 的 vocab** —— 它們不是候選對照的
競爭者，混進去只會墊高 `equity`／`interest`／`amount` 的 df、壓低 idf，靜靜翻掉別的
科目上千格適用性判定（見 v1.7→v1.8 那兩次事故）。但 **tag2concepts 要收**，否則工具
會以為那條 derive 從不成立，憑空多報 649 家 n/a —— 模型與管線脫節就是這樣來的。

**規則：某一格與加權平均差 >20%，且另一個獨立申報來源落在錨的 10% 內 → 換成它。
找不到就原封不動。** 四道閘門，每一道都是撞到才加的：

1. **錨是加權平均股數，不是隱含股數（淨利÷自報 EPS）**。隱含股數在少數股權大的

   推翻正確的封面股數。有了這道，錯的錨不會有任何候選同意它，規則自動不作用。
4. **期中增資要放行，但要有正面證據**：下一期的加權平均得往同方向跨一階（≥10%）。
   只看「下一期比較接近」不夠 —— Lazard 期末長期比加權平均高 15–18%、加權平均

換得掉就換、換不掉就刪成 n/a。**留白比混基礎誠實**——混基礎的每格單獨看都正常，
市值圖卻憑空跳一階，沒有任何欄位標示得出來。同理，這些格子若**連錨都沒有**
也一律刪（Clearway FY2021 前兩期）：判不了不等於沒問題，這個來源在這一列有前科。

**位置：仲裁必須排在「申報單位還原」與「沿用前期」兩者之後。** 前者讓加權平均

### 分割偵測：先前對 HURA／CVNA 的判斷兩個都錯（2026-08-21）

上一節說「殘餘壞格的頭部是分割沒偵測到（HURA、CVNA）」。做了 `computeSplits` 的
Python 鏡像（`sp3.py`，逐行對抄，13 個已知真分割與 7 家純分拆全部重現）之後，
兩個判斷都被推翻：

| | 先前說 | 實情 |
|---|---|---|
| CVNA | 5:1 分割沒偵測到 | **對，但原因不是門檻** —— 三個訊號全瞎 |
| HURA | 反向分割沒偵測到 | **既漏又誤**：真事件是 1:35，偵測器卻生出一個假的 ×8 |

#### CVNA：三個訊號同時失效的型態

多股別（Up-C）公司 → `CommonStockSharesOutstanding` 只有 2017 年兩筆 0、
`dei:EntityCommonStockSharesOutstanding` **一筆都沒有**（都帶維度被剝掉）、
單季加權平均稀疏到跨不過界線。訊號 A/B/C 各自的前提都是「同一期在兩份申報都出現」，
CVNA 在分割前後沒有任何一期符合。

分割是真的，證據在**跨粒度**：

    2025-12-31 年度加權平均  137,634,000  filed 2026-02-18（分割前）
    2025-06-30 單季加權平均  677,070,000  filed 2026-07-29（分割後，÷5 = 135.4M）
    2026-06-30 單季加權平均  717,691,000  filed 2026-07-29（÷5 = 143.5M）

年度與單季加權平均是同一種基礎，水位本來就可以比 —— 但三個訊號一律只做
「同一期跨申報」，**跨不了粒度**，所以看不見。

#### HURA：1:35 不在 CLEAN 清單，結構上偵不到

`detectSplit` 的 CLEAN 是 `[2,3,4,5,6,7,8,10,12,15,20,25,30,50]`，
刻意只收「公司實際用過的整數」（見 [[split-detection-double-apply]]）。
HURA 2024-10-18 的 1:35 不在裡面 → 永遠回 null。同時
2024-09-30 單季 1,586,000（filed 2024-11-14）對 12,178,522（filed 2025-11-14）
比值 7.68 落在 8 的 8% 內 → **生出一個不存在的 ×8**。
另外 dei 在 2024 年的兩筆是 55,660,578,000／42,284,524,000，**1000 倍申報單位錯**
（[[share-count-scale-and-tag-traps]]）。

#### 收緊後的第四個訊號：只抓「申報新舊不一致」的形狀

裸的「相鄰兩期差乾淨倍數」在羅素 3000 命中 691 個／457 家 —— 全是 IPO 前股本重組
與反向併購換股，不能用。加兩個條件收緊：中間那期的值**出自比兩邊都舊的申報**，
且對兩邊是**同一個**乾淨倍數（真發股不可能發完又收回）。
命中降到 **7 個／6 家**，CVNA 在內且倍數與界線都對。

#### 獨立裁判：雅虎 chart API 的 `events=split`，零額外請求

`prices.ts` 已經在打 `query1.finance.yahoo.com/v8/finance/chart`，
加 `&events=split` 就多回除權日與確切比例，**同一個請求**。它與 SEC 完全獨立
（交易所紀錄），正好補上 `sharesAcross` 在多股別公司無據可依的空缺。

實測：13 個已知真分割全中（除權日比偵測器的 threshold 早 0–120 天，因為 threshold
是分割後第一份申報）；7 家純分拆全無（GE 1.04、ZBH 1.03 那種分拆價格調整用
「必須是乾淨倍數」濾掉）；sp5 那 7 個候選裡正確確認 CVNA ×5、正確駁回
AMCR／WEST／RGTI／TBCH。

#### 但兩邊都不能當唯一真相 —— 這是下一步的岔路

抽樣 180 家（有事件 120 ＋ 無事件 60）：**一致 94、偵測器獨有 47、雅虎獨有 10**。

- **雅虎不能當否決權。** HON 2025-06-30 單季加權平均 637,500,000（filed 2025-07-24）
  被 2026-07-23 的申報重編成 318,800,000 —— 剛好一半，同一期跨申報，
  按偵測器的核心前提就是分割。雅虎沒有這筆。照雅虎否決會弄壞霍尼韋爾。
- **偵測器也不能當唯一真相。** BRO（Brown & Brown）生出 2018-05-10 ×0.02（1:50），
  近期單季 282M→283M→292M→331M 一路平順，1:50 顯然不存在。

**兩邊都有獨有事件、都有錯**，所以正解是仲裁不是取代 —— 與

#### 為什麼 A2 得拆成兩格

原本的四格表寫「裁判確認 → 採用」。多量一個**證據貼合度**
`dev = |實測比值 / 倍數 − 1|` 之後，這一格明顯不是同質的：

    A1（雅虎背書）  n=279  中位 0.0000   ≥2% 的只有 7 個
    A2（雅虎否認）  n= 79  中位 0.0357   ≥2% 的有 48 個

真分割把同一期股數**原封重述成整數倍**，比值本來就該乾淨；`detectSplit` 的 8% 容差
寬到會把發股、換股、SPAC 增資一起收進來。照原規則這 63 個會全部上線：

- **HURA 假 ×8**（dev 4.0%）—— 真事件是「新增」那格的 1:35
- **SIRI** 把真的 1:10 認成 1:12（dev 5.2%）。雅虎有真的那筆 → 丟掉錯的、新增對的。
  兩件事同時做才對：只丟不補會少一次分割，只補不丟會連乘成 120 倍
- **KDP** 2018-08-07／08 兩天內生出 ×0.0333 與 ×30（Keurig/Dr Pepper 換股）
- **OUST** ×7、1:7、×7 三連（SPAC）

門檻取 **0.1%**，餘裕留給申報單位捨入 —— HON 是 637,500,000 → 318,800,000 ＝ 0.50008，
dev 0.0002，通過。A2a 那 16 個的共同形狀是**分割夾在分拆/重組裡**，雅虎把它記成
`10000:9947` 這種零碎比例（HON 的五筆事件全長這樣），被「必須是乾淨倍數」濾掉。
這就是雅虎不能有否決權的機制。

#### 三個實作細節，少任何一個都會量錯或做錯

1. **`dev` 與 `devRaw` 兩個都要貼。** NAPCO（NSSC）只做過一次 2:1（2022-01），
   偵測器卻在 2023-02 與 2023-09 各生一個 ×2。`sharesAcross` 拿任何跨界線的配對當
   證據，**2022 那次的重述配對照樣跨得過 2023 的界線** → `dev` 是 0，但生出這兩個群的
   原始觀測 `devRaw` 是 6.3%／4.5%。只看 `dev` 會把 NSSC 的股數多乘兩次 2。
2. **涵蓋判準比對 `threshold − 200 天`，不是 `threshold`。** 除權日比申報界線早

   「雅虎否認」（BF.A/BF.B 2016-08-31 對視窗起點 2016-08-22）。修完 A2 從 100 降到 79。
3. **`coverStart` 不能省。** 少了它，改名或重新上市的公司會被誤當成「雅虎說沒有」
   而誤刪真事件。`coverStart` ＝ `firstTradeDate` 與本次視窗起點的**較晚者**。

另外有個 Windows 專屬的坑：`datetime.fromtimestamp` 遇負 epoch 丟 OSError，
1970 年前上市的公司 `firstTradeDate` 是負的（HON 是 −252322200 ＝ 1962）——
HON、KO、JNJ、IBM… 28 檔老牌大型股整批被吞掉，**正好包含要驗證的 HON**。
TS 那邊 `new Date(sec * 1000)` 沒這個問題，但註解寫著別改成會踩平台限制的寫法。

所以 Copart 2022／2023 連兩次真 2:1（各自配到自己的雅虎事件）不會被誤併。全母體 5 個。

### 長期負債那四季：兩條規則量完只上一條（2026-08-21）

使用者指名 PANW 的 EV／EV-EBITDA（FY2024Q4–FY2025Q3）、ROIC、利息保障倍數是 n/a。
三個都追到底，**結論不一樣**：一個修好、一個是誠實留白、一個順手挖到更嚴重的錯數字。

#### 利息保障倍數 → 修好（改成「—」）

利息費用為 0（PANW 還清可轉債後就是 0），營業利益 ÷ 0 的 `#DIV/0!` 被 IFERROR
吃掉寫成 n/a。但「沒有有息負債」不是「查不到」。加 config 欄位
`inapplicable_if_zero`，`formulas.py` 包成 `IF(分母=0,"—",IFERROR(...))`。
分母若是 `"n/a"` 文字，`="n/a"=0` 為 FALSE → 仍走 IFERROR 回 n/a，兩種留白不會混。

離線量看起來很漂亮：長期負債命中 4,091 期／509 家，加上「證人否決」（該期末日若有
其他債務標籤金額超過另一段的 1.2 倍就維持 n/a）擋掉 174 期，JPM 467 億、CVS 305 億、

**「不知道會錯多少」**，這個有恆等式可以答：長期債是非流動負債的子集，所以

```
看不到的長期債 ≤ 負債總計 − 流動負債合計 − 長期租賃負債
```

這是上限不是估計。上限佔市值夠小 → 視為 0，對估值的影響有界；上限太大或算不出來
→ 維持 n/a。**JPM 是自動擋掉的**：銀行的資產負債表不分流動，沒有「流動負債合計」，

  99.9% 扣完仍 ≥ 真值，短期 30,343 期裡 99.5%。

  （NetApp 上限 668M、真實長期債 1,144M），扣過頭就不再是上限，整條論證就沒了。
- 實測：PANW 4 期、VRTX 22 期、MRNA 15 期開槍（後兩者本來就無債）；

#### 順手挖到的真錯：`LongTermDebt` 是含流動部分的總額（已修）

比 n/a 嚴重得多，因為它顯示的是**看起來正常的錯數字**：

| | 短期借款 | 長期負債 | 顯示的總債務 | 實際 |
|---|---|---|---|---|
| PANW FY2022Q1 | 3,672M | 3,672M | 7,344M | 3,672M |
| BA FY2021Q1 | 5,446M | 63,000M | 68,446M | 63,000M |

us-gaap 的 `LongTermDebt` 定義是「含流動部分」，它排在對照表第二順位，
`LongTermDebtNoncurrent` 缺席時就會取到它，跟短期借款那一列重複計算，
淨負債、負債權益比、ROIC、EV、EV/EBITDA 全部跟著錯。

修法**不是換優先序**：全母體量過，把總額標籤降到專用非流動標籤之後會動到 4,027 期，
但只有 41% 對得上 —— 專用標籤常常只是債務的一部分（同一家把長期債拆成擔保／無擔保

### MP 的 Magnetics 整排 n/a：只有一種產品的分部沒有小計（2026-08-22）

使用者回報 MP Materials 的分部分頁 FY2025 上半年整排空白，但財報上兩個分部都有數字。
追到申報檔，**事實在，是我們的抽取規則把它全部丟掉了**。

同一份 10-Q 裡，MP 的兩個分部長得不一樣：

| 成員 | 可用的事實 | 抽取器 |
|---|---|---|
| Materials | `ConsolidationItems=OperatingSegments + BusinessSegments=Materials` = 37,532M | 單一分部軸 → **收** |
| Magnetics | `… + ProductOrService=MagneticPrecursor` = 19,861M | 兩個分部軸交叉 → `cross_axis` 丟 |
| Magnetics | `… + srt:MajorCustomersAxis=mp:ExternalCustomers` = 19,861M | 設定外維度 → `foreign_dim` 丟 |

原因很單純：**Magnetics 只有一種產品**，所以申報人沒有另外標一個分部小計 ——
產品那一行就是分部那一行。Materials 有三種產品，才有獨立的小計事實。

而且這是**比較期**才會發生：FY2026 的 10-Q 裡當季兩個分部都有乾淨小計，
但 2025 年的比較期只有上面那兩種標法。加上合併規則「成員集合鎖在最新那份申報」
（避免改組公司新舊結構疊加），舊申報也補不回來 → 整排 n/a。

修法走設定層（`config/segment_axes.json` 1.5 → 1.6），兩件事：

1. `passthrough_dims` 多一個 `patterns`：成員是公司自訂時白名單列不完
   （`mp:ExternalCustomersMember`），改比對成員裸名的正規式。目前只放行
   `MajorCustomersAxis` 底下的 `^External`。
   **不放行 Intersegment** —— 那是分部間銷售，只是分部營收的一部分。
   外部客戶營收不含分部間銷售，反而比分部總額更容易與合併總額對得起來
   （合併營收 ＝ Σ 外部客戶）。
2. 抽取器加「乾淨事實優先」：同一格若也有單軸的分部小計，一律以小計為準，
   passthrough 只補真正的空格。這道防護是必要的 —— MP 同一份申報裡 Materials
   既有小計 95,629M、也有外部客戶 91,966M（差的 3,663M 是分部間銷售），
   文件順序是「小計 → 外部 → 小計」，靠原本的「後寫贏」等於擲骰子。

結果：MP 的 Magnetics FY2025 Q1／Q2 補回 5,191M／19,861M，
Materials 維持 95,629M 沒有被外部客戶數字蓋掉。

118 家逐格回歸（`segment_sweep` 重解析 ＋ `segment_diff`）：
**數值改變 0 格、校驗狀態變化 0 家**，唯一的差異是 CMI 多了 62 格 —— 而那格差異
挖出了另一個更廣的問題。

#### 分部快取的 key 少綁了一個設定檔（同批修掉）

CMI 多出來的 62 格是**分部折舊攤銷**，數字與 10-K 完全相符。它本來就該有：
`OtherDepreciationAndAmortization` 早在 map v1.8（commit `416daf3`，「補 15 個標籤」）
就進了對照表。沒出現的原因是分部快取的 key 只綁 `segment_axes.json` 的版本：

```
seg/v5-${cfg.version}/${cik}/${accession}.json      ← 舊
seg/v6-${cfg.version}-m${mapVersion}/…              ← 新
```

抽取要不要收一筆事實，取決於它的標籤有沒有對到 concept —— 而那份對照表是

而且不會有任何錯誤訊息**。程式裡原本就有一段註解在警告這個失效模式，只是防到了
另一個檔（segment_axes）。v1.8 那批 15 個標籤實際生效的只有從沒被快取過的公司。

- **名稱形狀沒有鑑別力。** 含 `And…`／`Including` 的比例：通過組 72%、擋下組 78%。
