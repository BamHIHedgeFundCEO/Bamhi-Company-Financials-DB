# 產品路線圖

> **狀態：v1 已上線，下表的「待做」是撰寫當時的狀態，未回填。**
> 目前正在執行的分階段計畫見 **[`PHASE_PLAN.md`](PHASE_PLAN.md)**（階段之間的交接文件）。
> 這份檔案保留為策略層的判斷原則。

## 定位

**這不是一個財報下載器，是 EDGAR 的繁體中文入口。**

v1 蓋完之後，你手上有的是一整條 pipeline：ticker 解析、CIK 對照、限速控制、快取、XBRL 剖析、Excel 生成。**EDGAR 上不只有 10-K 和 10-Q。** 每多支援一種表單，邊際成本接近零，而繁中市場的競爭者是零。

所有排序都從這個定位推導。

---

## 判斷是否要做的三個標準

任何新功能進來之前，先過這三關：

1. **它複用既有 pipeline 嗎？** 複用 = 成本低。要接新資料源、新付費 API = 成本高
2. **繁中市場有人做嗎？** 有人做且做得好 = 沒有理由做。沒人做 = 機會
3. **它會讓使用者回來嗎？** 一次性功能不值得優先，留存機制值得

**「使用者很想要」不是充分理由。** 需求高但護城河低的功能（見下方估值倍數）會消耗你的時間卻換不到防守位置。

## v1.5（成本極低，先做）

### 錯誤回報按鈕

「原始資料」分頁與網頁結果表加一個一鍵回報。使用者發現某科目取錯值，一鍵送出 → 你收到 `ticker + 科目 + 期間 + 目前取到的標籤`。

**這是整個專案唯一會隨時間複利的東西。**

功能可以被抄，`xbrl_zh_map.json` 抄不走——因為它是幾百個真實使用者踩過坑之後長出來的。愈多人用，它愈準；愈準，愈多人用。

工程量：一個 form + 一個 webhook。半天。

## v2（依序執行，不要平行）

### 1. 跨公司比較

輸入 `NVDA, AMD`，同樣的 31 個指標、同樣的季度軸，兩家併排成一張表加對比圖。

- **複用度**：極高。資料結構已完全支援，只是多跑一次 pipeline 再併欄
- **理由**：使用者拿到 NVDA 的 Excel 之後，下一個念頭幾乎必然是「那 AMD 呢」。這是最自然的下一步
- **上限**：同時 3 家（超過在表格與圖表上都難讀）

### 2. 新財報 Email 通知

使用者訂閱幾檔股票，SEC 一有新的 10-Q / 10-K，寄信通知並附上該期間的 Excel 下載連結。

- **複用度**：高。每日一支排程比對 `submissions.json` 即可
- **理由**：**這是留存機制**。v1 的所有功能都是一次性的——查完就走。這個功能把訪客變成回訪者
- **附帶效果**：email 欄位終於有正當用途（而不是像早期想過的那樣拿去填 User-Agent）

### 3. Form 4 內部人交易

高階主管與董事的買賣申報。EDGAR 免費提供，同一條 pipeline。

- **複用度**：高。同樣的 CIK、同樣的 submissions API，只是換 form type 與剖析邏輯
- **理由**：繁中投資圈需求高，但幾乎沒有像樣的中文工具。「執行長賣股」是永恆話題
- **注意**：Form 4 是 XML 不是 XBRL，剖析邏輯要另寫

### 4. 13F 機構持股

基金經理人的季度持股申報。

- **複用度**：中。資料源相同但結構完全不同（持股清單而非財務報表）
- **理由**：「巴菲特這季買了什麼」在繁中社群是永恆流量，SEO 價值極高
- **注意**：13F 有 45 天延遲，且只揭露多頭部位，呈現時必須標明這兩點，否則會誤導

### 5. 分部數據（Segment Reporting）

NVDA 的 Data Center 對 Gaming、AAPL 的服務對硬體。

- **複用度**：低。**`companyfacts` API 不含維度資料**，必須直接剖析申報的 XBRL instance 檔
- **理由**：**這是真正的護城河。** 正因為麻煩，幾乎沒有免費工具做得好。而做研究的人最想看的就是這個
- **判斷**：「難做」本身就是防守位置。前四項別人能在一個月內抄走，這項不行

### 6. 估值倍數（P/E、EV/EBITDA、P/B）

- **複用度**：低。需要股價資料源，涉及付費、授權條款、股票分割與股息調整
- **理由**：**需求最高，但護城河最低。** Yahoo Finance 免費給，每個券商 App 都有
- **判斷**：該做，但排最後，**而且不要拿它當賣點**。你在這件事上沒有任何優勢

## 明確不做

| 項目 | 條件 |
|---|---|
| 登入與訂閱制 | 除非已經有人開口說要付錢 |
| Queue 與分散式限流 | 除非真的在 log 看到 429 |
| 手機 App | 這種工具在桌機用，做 App 是浪費半年 |
| PDF 轉檔 | 見 v1 規格：把好抽的資料轉成難抽的格式 |
| Google Sheets API 整合 | 需要 OAuth + Drive 安全審查，換來省一次上傳 |

---

## 決策原則

**新功能一律先問：能不能只改 JSON 就完成？**

三個設定檔（`xbrl_zh_map.json` / `chart_spec.json` / `theme.json`）是這個產品能否規模化的判準。如果一個需求必須改程式碼才能滿足，先想想是不是設定層的抽象做錯了。

**先上線，再優化。** 這份路線圖的每一項都比不上「v1 真的有人在用」重要。
